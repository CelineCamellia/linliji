# 开发记录与取舍

## 从便民目录到居民发布

最初结构覆盖商品目录、维修预约和闲置发布。实际使用场景更接近社区居民之间互相提供手艺、转让物品和交换东西，不依赖商家先入驻，因此首页和主流程改成三类居民发布。原商品和预约代码保留在开发演示模式，用于既有回归；正式页面不提供付款或履约入口。

三种发布共用账号、城市、社区、描述、照片、联系方式和审核状态。差异集中在 `listingFields`：买卖有固定金额；手艺可固定、面议、免费；交换需要填写想换什么。金额以整数分保存，避免浮点金额误差，也避免把“面议”和“交换”误画成零元出售。

## 本地验证与部署采用同一主流程

`quickstart` 创建空库、随机管理员密码和本机配置，直接运行 production 模式的注册与审核。它只监听回环地址。本地跑通后，公网部署更换配置和 HTTPS 入口，不需要换一套业务实现。

安卓包不固化开发电脑 IP 或假的服务域名。首次填写服务地址时先检查健康接口和站点配置，成功后再切换；不同服务的登录会话分开保存。这样开源项目能被不同社区独立部署，安装包也不依赖维护者长期提供公共服务器。

## 为什么照片没有直接保存原文件

手机原图可能很大，还可能包含拍摄位置等元数据。上传后由 Sharp 解码，校验静态格式、限制尺寸、压缩为 WebP；图片路径由服务端生成。照片与发布分开保存，先上传再在发布事务中绑定，防止借用其他账号的照片。

审核前原始公开路径返回 404；本人用短期签名预览，管理员通过独立接口查看。修改公开信息会回到 pending，所以重新改过的内容不能绕过审核。

## 管理方式

早期仅有回环地址上的本机管理工具。为了部署到服务器，增加同源 `/admin/`，复用审核与举报操作，并在入口添加管理员身份、Cookie、同源提交和退出撤销。原本机工具仍可用于离线维护，不能直接代理到公网。

## 本次排错记录

- Multipart 解析器的分段上限可能把正常单文件表单误认为超限，调整上限后增加真实 FormData 上传检查。
- 修改后重审曾显示上一轮通过理由；现在居民状态说明只展示驳回或下架原因，完整历史留给管理员。
- 原来的固定城市导致其他城市无法选择社区；社区选择改成按城市独立保存，并忽略切城前还未完成的请求结果。
- 旧备份仅覆盖数据库；现在根据数据库快照复制照片，并提供摘要校验与拒绝覆盖的恢复工具。

这里记录实现顺序和实际问题，不补造历史提交、用户量或性能指标。版本验证范围见 [测试说明](testing.md)。
